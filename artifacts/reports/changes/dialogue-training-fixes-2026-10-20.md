# 메시지 선노출 / Run 능력 포인트 저장 수정

## 메시지 원인과 수정

실제 선노출/재타이핑의 확정 원인은 타이핑 시간 계산이었다. layout effect에서 기록한 `performance.now()`보다 첫 `requestAnimationFrame` 콜백의 프레임 시작 시간이 조금 이를 수 있다. 이때 글자 수가 음수가 되고 `characters.slice(0, -1)`처럼 동작하여 문장 대부분을 먼저 보여줬다. 이후 프레임에서 글자 수가 0, 1, 2로 바뀌면서 화면이 비워지고 다시 타이핑됐다.

앞선 빈 최초 렌더 검사만으로는 첫 콜백 이후의 역행을 발견하지 못했다. 영입/출전 준비를 정상 속도로 실행하고 모든 텍스트 변화를 기록하자, 같은 DOM 노드에서 20글자 → 0글자, 영입 결과에서 문장 대부분 → 0글자가 되는 것을 PC/모바일 모두 재현했다.

수정은 첫 RAF 콜백의 시간을 시작 시각으로 삼아 시간 기준을 통일하고 글자 수를 0 이상으로 제한하는 것이다. 새로운 회귀 테스트는 문장 전체 수명 동안 표시 글자 수가 줄지 않는지 검사하며, 프레임 시각을 100ms 앞당긴 조건에서도 검사한다.

별도로 기존 완성 문장의 숨김 span/속성/닫힌 기록, 이벤트·레이드의 중복 안내, 문자열만 사용하던 인스턴스 구분도 정리했다.

수정 사항:

- 현재 메시지는 `characters.slice(0, count)`로 만든 표시 문자열 한 곳에서만 렌더한다. 숨김 완성 문장과 `data-full-text`는 제거했다.
- 배틀 기록은 사용자가 열었을 때 내용을 렌더한다. 기록 기능과 HP 등의 상세 기록은 유지한다.
- 이벤트 장면의 별도 summary와 레이드의 중복 대사는 제거했다. 대상 이미지, 장면, 제목, 보상 안내는 유지한다.
- `GameDialogue.messageKey`를 추가했다. 배틀은 Run/층/상태/배틀/장면과 프로토콜 인덱스, 이벤트는 이벤트 ID/phase/mode, 영입은 Run/배틀, 상점은 이벤트/상품/구매 상태로 구분한다.
- React key는 메시지 인스턴스·문자열·애니메이션 모드를 함께 사용한다. 새 인스턴스의 state initializer는 count 0으로 시작하며, 기존 `useLayoutEffect`도 최초 paint 전에 초기화한다. 첫 렌더에 이전 문장이나 새 완성 문장을 재사용하지 않는다.
- 대사 내용은 key의 DOM 속성에 넣지 않는다. `data-message-key`는 인스턴스 식별자만 가진다.
- 접근성용 완성 문장 복사본 대신 실제 표시 문단을 읽도록 하고, 타이핑 중에는 live 안내를 끄고 완료 시 켠다.
- 타이핑 중 Z/Enter/클릭은 문장 완성만 수행하며 다음 단계는 다음 입력으로 진행한다. 별도 모달의 조작 키를 배경 메시지가 가로채는 동작은 추가하지 않았다.
- 애니메이션 감소 설정과 기존 메시지/전투 재생 속도는 유지한다.

적용 경로: 일반 배틀, 배틀 시작, 보스/히든 보스 조우, 빌런 조우와 승리 후 후속 대사, 레이드 조우/결과, 일반 이벤트 결과, 승리 보상·영입 결과, 층 이동·출전 준비·정비 진입, 히든상점 대화.

## 능력 포인트 원인과 수정

HP 등 6개 행은 이미 도감과 같은 `SettingsPicker(kind: 'ev')`에 연결되어 있었다. read-only prop이나 IV 편집기로 잘못 연결된 문제가 아니었다.

실제 오류는 서버 저장 검증의 기준이었다. Run 설정 화면은 이번 도전의 개체 프로필을 전송하는데, `TowerStore.train`은 그 IV를 영구 도감의 IV와 비교했다. 도감에만 등록하거나 레이드 개체를 얻은 뒤에는 두 프로필의 IV가 정상적으로 다를 수 있다. 이 차이를 사용자의 IV 수정으로 오인하여 “개체값은 상대 포켓몬 영입으로만 높일 수 있습니다.” 오류로 거부했다.

수정 사항:

- Run 조정은 현재 Run 프로필을 검증·비용 계산의 기준으로 삼는다. 도감 설정은 기존 영구 프로필 기준을 유지한다.
- 요청의 IV가 해당 기준에서 바뀌면 여전히 거부한다. IV 직접 편집 기능은 추가하지 않았다.
- 능력 포인트 등 편집 가능한 설정을 저장하면서 Run IV와 영구 도감 IV는 각각 보존한다. Run 저장 때문에 영구 IV가 낮아지거나 영구 IV를 현재 개체에 임의 적용하지 않는다. 이로치 상태도 각 프로필의 기존 상태를 유지한다.
- 가격 공식, 전체 66/항목 32 제한, 성장 포인트 차감, revision·snapshot 검증, 폼 변경 금지와 전투 중 저장 차단은 유지한다.
- 이미 생성된 배틀의 팀/상태를 수정하지 않는다. 정비/출전 준비에서 저장한 Run 프로필은 다음 `enter`의 팀 생성에 반영한다.
- `RunPokemonSettings` → 공통 `PokemonSettings` → 같은 능력 포인트 편집기를 계속 사용한다. 폼체인지는 Run에서 숨김, 취소 후 카드 포커스, 성격/성별/기술/특성/테라 설정도 유지한다.
- 영입의 IV 비교·도감 병합 코드는 변경하지 않았다.

## 검증

- 단위·도메인 32개 통과: 서로 다른 영구/Run IV의 양방향 사례, IV 직접 수정 거부, 저장 비용, 두 프로필의 IV 보존, 과거 배틀 팀 불변, 다음 전투의 포인트/IV, 66/32 제한, 기존 영입 IV 병합, 레이드 영입, 폼·기술·배틀 아이템 회귀.
- 서버 렌더 테스트: 최초 HTML에 완성 문장·숨김 복사본·완성 문장 속성이 없고, 닫힌 기록도 비어 있는지 확인했다. 기록을 명시적으로 여는 경우에는 전체 기록을 렌더한다.
- 이전 관련 브라우저 테스트 53개에 더해, 정상 속도의 영입/출전 준비 연속성 회귀 테스트 2개를 추가했다. 시간 계산 수정 후 메시지 관련 14개가 모두 통과했다.
- PC 1280px / 모바일 390px에서 브라우저 시계를 멈추고 MutationObserver로 각 메시지 노드의 최초 렌더를 수집했다. 첫 문단이 빈 문자열인지, 이전/새 메시지가 겹치지 않는지 확인한다.
- 최초 렌더 검사 경로: 승리 보상, 영입 결과, 출전 준비/층 안내, 배틀 시작, 정비 진입, 일반 이벤트 시작/결과, 빌런 조우/승리 결과, 레이드 조우.
- 같은 테스트에서 Z/Enter/클릭 첫 입력은 완성만 하고 두 번째 입력은 진행하는지 확인했다.
- 정비와 출전 준비 X 설정에서 6개 행 모두 편집기가 열리고 취소되는지, 실제 저장/재진입/폼 보존/포커스 복원이 되는지 확인했다. 영구 IV가 31이고 Run IV가 0인 사례로 재현했다.
- 도감 통합 설정, 영입, 레이드, 로켓단 연쇄, 숨겨진 보스, 배틀 기록, 1/2/4배속 효과 대사의 관련 브라우저 회귀 검증을 수행했다.
- 프로덕션 빌드, TypeScript, CSS 구조 검사, `git diff --check` 통과.

## 직접 확인할 화면

1. 빌런/레이드 조우와 승리 후 후속 문구: 처음에는 빈 메시지에서 타이핑되고, Z 한 번은 완성만 해야 한다.
2. 영입 → 도감에 넣기 → 결과 확인 → 다음 층 준비: 결과와 다음 층 안내가 겹치거나 완성 문장으로 번쩍이지 않아야 한다.
3. 정비의 포켓몬 조정 및 출전 준비 카드에서 X: HP/공격/방어/특공/특방/스피드 편집 → 적용 → 저장 → 다시 열기. IV 오류가 없어야 하며 폼체인지가 노출되지 않아야 한다.
