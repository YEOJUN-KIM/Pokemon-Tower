## 승리와 보상 흐름

승리일 때 BattleResultDialog와 ResultBanner를 렌더링하지 않는다. 패배/무승부 및 재도전 결과창은 유지한다. 배틀 재생이 끝나면 후보 선택 화면을 자동으로 연다. 후보 화면은 기존 GameDialogue로 “배틀에서 승리했다! N코인을 얻었다.”를 표시하며 추가 보상 확인창을 만들지 않는다. 코인 지급 자체는 기존 서버 complete 트랜잭션 그대로다.

레이드에서는 코인 문구를 만들지 않고 짧은 승리 문구만 표시한다. 영입 또는 건너뛰기 이후 기존 이벤트 보상 화면을 그대로 사용한다. 기존 레이드 보상 dialog는 이벤트 보상 내용 확인을 위한 화면이며 일반 WIN 결과창과 구분된다. 히든보스 및 빌런 진행/보상 조건도 기존 서버 흐름을 유지한다.

## 후보 선택과 저장

일반 배틀은 기존 후보 3마리를 가로 카드로 표시한다. 레이드는 기존 규칙의 보스 후보 1마리를 유지한다. 후보의 Z/Enter/클릭은 작은 컨텍스트 메뉴를 연다:

1. 동료로 데려가기
2. 도감에 넣기
3. 포켓몬 정보
4. 취소

하단 고정 액션 버튼, 별도 정보 버튼, 영입/도감 등록의 재확인 dialog를 제거했다. 두 등록 액션은 즉시 기존 POST /api/battle의 recruit 동작을 호출한다. collectOnly, chosen, replaced, runId, battleId의 기존 계약을 사용한다. 6마리 제한에서는 기존 교체 대상 선택 화면만 유지하며, 대상을 고르면 곧바로 처리한다. 동일 종이 이미 Run에 있으면 기존 성장 병합 규칙을 따른다.

IV 최대값 병합, 기술 해금, 영구 도감, Run 합류/교체, 영입 수, 보상, DB 구조 및 트랜잭션은 변경하지 않았다. 저장 요청 중에는 후보 화면을 유지해 종료된 배틀로 되돌아가는 공백도 방지한다. 오류는 기존 error 영역으로 표시하고 후보에서 재시도할 수 있다.

## X 건너뛰기

후보 화면의 X/Esc 또는 닫기는 “영입하지 않고 넘어가시겠습니까?”만 연다. 기본 커서는 취소다. 취소하면 직전 후보 커서로 돌아오고, 넘어가기는 chosen:null인 기존 recruit를 실행한다. 끝난 배틀 화면으로 닫히지 않는다. 메뉴의 X는 메뉴만 닫고, 정보의 X는 후보로 복귀한다.

## 후보 정보와 짧은 결과

기존 PokemonSummary에 선택적 비교 데이터를 전달한다. 후보의 이름·폼·이미지·타입·성별·특성·성격·기술을 재사용한다. 후보 IV와 보유 도감 IV는 서버가 이미 제공하던 candidateIVs / collectionIVs를 표시한다. 보유한 종인 경우 “기존 → 후보”를 표시하고 더 높은 값에 청록 테두리와 ↑를 함께 붙인다. 미보유 종은 후보 IV만 표시한다.

미수집 기술은 기존 collectionMoves와 기술 ID를 정규화해 비교하고 NEW를 붙인다. 새 종은 후보 카드에 NEW를 표시한다. 방향키와 PageUp/PageDown으로 긴 정보 화면을 스크롤할 수 있다.

결과창은 이미지와 “이/가 동료가 되었다!” 또는 “의 정보가 도감에 등록되었다.” 및 계속 버튼만 사용한다. 기존 도감 갱신 문장, 새 기술 개수/개별 목록, IV 최대값 유지 설명, 팀 합류/다음 도전 안내, 영입 후 전체 멤버 목록을 제거했다. 비교 정보는 후보 정보창에서만 확인한다.

## 다음 층과 footer

새 층 화면에는 “N층에 출전할 3마리를 선택하세요.”와 선택 수, 멤버 카드, 진행 액션을 남겼다. 지역/세대 테마 문장, 보유 멤버 수 설명, 첫 번째 선봉 설명, 닫기 X/뒤로가기를 제거했다. 선봉은 01 선봉으로 표시한다. X/Esc로 출전 선택 단계를 닫을 수 없으며 3마리를 골라 기존 enter API로 진행한다. 정비/배낭 안의 하위 메뉴 닫기는 유지한다. 이벤트 뒤에 기존 빌런 급습이나 히든보스 자동 전투가 이어지는 경우에는 새 출전 선택을 끼워 넣지 않고 그 진행을 유지한다. 이벤트 테스트도 이 기존 분기를 구분해서 확인한다.

배틀 화면도 도감의 GameMenuProvider / GameMenuBar를 사용한다. dialog별 로컬 footer는 자동 생략되며 화면 아래 하나의 footer가 활성 context를 표시한다: recruit-candidates / recruit-menu / recruit-info / recruit-skip / recruit-replace / recruit-result / floor-team. 실제 키 입력은 기존 useGameKeyboard와 game cursor를 사용한다.

## 플레이어 HP 창 구조 분석 — 이번에는 변경하지 않음

HealthCard(`src/web/battle-pokemon.tsx`)는 플레이어/적이 같은 컴포넌트를 사용한다. 이름+성별+타입, Lv.50, 상태이상, HP 바, HP 수치, 잔여 멤버 볼 순서다. 플레이어는 체력 수치, 적은 퍼센트를 사용하며 현재 플레이어 체력도 연출 중에는 퍼센트로 표시한다. 테라 관련 타입은 currentTypes를 따르고 특수 변신 표시는 주로 스프라이트/연출에 있다.

1280px/390px 실제 배틀 화면을 확인했다:

- 정보 자체가 비어 있지는 않다. 무상태일 때 상태이상 행이 생략되고 적/플레이어의 남은 볼 수가 달라 공간 밀도 차이가 생긴다.
- 데스크톱에서는 이름·성별·타입·레벨이 한 줄에 들어간다. 모바일 플레이어는 타입이 다음 줄로 내려가 이름/타입 묶음과 우측 레벨 정렬이 불균일해 보인다. 긴 폼 이름과 상태이상이 함께 있으면 추가 확인이 필요하다.
- 적과 플레이어가 같은 윤곽·색·HP 바 구조를 사용해 위계는 일관적이다. 플레이어의 정확한 HP 수치가 퍼센트로 바뀌는 연출 시점에는 정보 형식이 흔들릴 여지가 있다.
- HP 창은 기존 각진 녹회색 게임 패널이고 일반 브라우저 HUD처럼 흰색 상자를 덧댄 구조는 아니다. 다만 알약형 타입 배지와 HP 트랙은 새 남색 메뉴보다 둥근 인상을 준다.
- 특수 상태를 전부 HP 창에 추가하면 오히려 좁은 모바일 이름 행이 복잡해질 수 있다. 후속으로 이름/성별/레벨과 타입/특수 상태를 두 행으로 명시 분리하고 플레이어 HP 표기 형식을 일정하게 하는 시안을 권장한다.

이 작업에서는 HP 디자인을 재설계하거나 배틀 판정/수치를 바꾸지 않았다.
